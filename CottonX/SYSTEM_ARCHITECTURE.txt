1. EXECUTIVE SUMMARY
================================================================================

CottonX is a multi-agent AI orchestration platform designed to enable autonomous
management of decentralized finance operations. The system provides:

• Four specialized AI agents (Eric, Harper, Rishi, Yasmin) for different DeFi domains
• Non-custodial wallet management via Coinbase Developer Platform
• Real-time bidirectional communication via WebSocket
• Natural language intent processing with intent routing
• Secure transaction execution on EVM-compatible blockchains
• Persistent audit trails and decision logging

The architecture replaces traditional serverless AWS infrastructure (Lambda, SQS,
DynamoDB, API Gateway, SageMaker) with a unified GCP Cloud Run deployment,
reducing operational complexity while maintaining scalability.

3.2 Backend Server (Express.js + WebSocket)
────────────────────────────────────────────────────────────────────────────────

Location: /backend/src/server.ts
Framework: Express.js with ws (WebSocket library)
Port: 8080
Deployment: GCP Cloud Run

Key Responsibilities:
  • HTTP API endpoints for health checks and status
  • WebSocket upgrade handling (query parameter validation)
  • Asynchronous message processing
  • Rate limiting (500 requests per minute globally)
  • Connection lifecycle management

HTTP Endpoints:
  GET /           - Status endpoint (returns active connections)
  GET /health     - Cloud Run readiness probe

WebSocket Handler:
  Path: /ws
  Query Parameters: sessionId, characterId (required)
  Authentication: Via sessionId (Firebase token validation in client)
  Message Format: JSON frames with "action" field
  Supported Actions: "sendMessage"

Rate Limiting:
  • Per-minute bucket reset every 60 seconds
  • Global limit: 500 requests per minute
  • Returns 429 on limit exceeded


3.3 Chat Processing Pipeline (queueChatExecutor.ts)
────────────────────────────────────────────────────────────────────────────────

Location: /backend/src/lambda/queueChatExecutor.ts

Main Function: processChat(payload: InvokeModelPayload)
  Input:
    - sessionId: Unique user session identifier
    - characterId: Selected agent/character ID
    - userMessage: User's natural language input

Processing Steps:
  1. Load character wallet from Firestore
  2. Initialize Multi-Agent Orchestrator
  3. Prepare agent registry with tools
  4. Invoke orchestrator.invokeAgent()
  5. Stream response chunks back to client
  6. Persist complete chat history
  7. Update character wallet state

Output: Streamed response via WebSocket + persisted in Firestore


3.4 LLM Provider Abstraction
────────────────────────────────────────────────────────────────────────────────

Architecture Pattern: Strategy Pattern - selectable LLM providers

Providers:

A. Google Gemini (gemini-agent.ts)
   • Model: Gemini 1.5 Flash
   • Inference Config: maxTokens (4000), temperature (0-2), topP (0.9)
   • Tool Format: Google Generative AI FunctionDeclarations
   • Features: Streaming, function calling, multi-turn conversations

B. OpenAI-Compatible (openai-agent.ts)
   • Provider: Featherless (deepseek-ai/DeepSeek-V3)
   • Base URL: https://api.featherless.ai/v1
   • Tool Format: OpenAI format (function definitions)
   • Features: Streaming, function calling, cost-effective

C. Classifiers (gemini-classifier.ts, openai-classifier.ts)
   • Specialized models for intent routing
   • Lower token usage (maxTokens: 4000)

3.9 WebSocket Connection Management (wsManager)
────────────────────────────────────────────────────────────────────────────────

Location: /backend/src/ws/manager.ts

Data Structure:
  Map<string, WebSocket>
  Key format: session#{sessionId}::character#{characterId}

Methods:
  • register(sessionId, characterId, ws)
    - Registers new WebSocket connection
    - Replaces existing connection for same session/character
    - Emits close handler for cleanup
  
  • sendMessage(sessionId, characterId, message)
    - Sends message to specific session/character pair
    - Returns boolean (success/failure)
    - Checks connection readiness (OPEN state)
  
  • isConnected(sessionId, characterId)
    - Checks if connection exists and is open
    - Used before sending messages
  
  • getActiveConnections()
    - Returns array of all active connection keys
    - For debugging and monitoring

Lifecycle:
  1. Frontend initiates WebSocket with sessionId & characterId
  2. Server validates parameters
  3. wsManager.register() stores connection
  4. Server broadcasts messages via wsManager.sendMessage()
  5. On close, wsManager automatically removes connection

Message Format:
  Outgoing (server → client):
  {
    "type": "message" | "error" | "status",
    "characterId": string,
    "content": string,
    "timestamp": number
  }

7. SECURITY ARCHITECTURE
================================================================================

7.1 Authentication & Authorization
────────────────────────────────────────────────────────────────────────────────

User Authentication:
  • Firebase Authentication (frontend)
  • Methods: Email/Password, Google OAuth 2.0
  • JWT tokens issued by Firebase
  • Token validation: Client-side (implicit trust assumption)

Session Management:
  • sessionId: Unique identifier per authenticated session
  • characterId: Selected AI agent for session
  • WebSocket connection validates both parameters
  • No token reauthentication required per message (streaming optimization)

Authorization:
  • Firestore security rules: Development mode (open)
  • Production: Should implement user-based access control
  • Document-level permissions for chat history isolation


7.2 Non-Custodial Wallet Architecture
────────────────────────────────────────────────────────────────────────────────

Private Key Management:
  • Coinbase Developer Platform SDK
  • Private keys never leave user's wallet
  • Agent cannot access raw private keys
  • Transaction signing happens at Coinbase service
  • User retains full control

Wallet Operations:
  • create-wallet: Generates new wallet address
  • Wallet encrypted at rest in Firestore
  • Only user who created wallet can authorize transactions
  • No agent can unilaterally sign transactions

Transaction Authorization:
  • Each transaction requires signing
  • Signed via Coinbase CDP
  • Agent prepares transaction parameters
  • Signing is non-custodial (user retains control)
  • No access to raw private keys in backend


7.3 API Security
────────────────────────────────────────────────────────────────────────────────

Rate Limiting:
  • Global limit: 500 requests per minute
  • Per-minute bucket reset every 60 seconds
  • Returns 429 on limit exceeded

Input Validation:
  • WebSocket messages: JSON validation
  • Query parameters: sessionId & characterId required
  • Chat messages: Sanitized before processing

HTTPS/WSS:
  • All traffic encrypted in transit (Cloud Run provides TLS)
  • WebSocket upgrade to WSS in production
  • Certificate management: Automatic (GCP managed)

CORS Configuration:
  • Express CORS middleware enabled
  • Configurable origins in production
  • Credentials: Same-origin only

Environment Variables:
  • API keys stored in .env files (development)
  • Cloud Run environment variables (production)
  • Never committed to version control
  • Rotate keys periodically


7.4 Data Security
────────────────────────────────────────────────────────────────────────────────

Chat Data:
  • Stored in Firestore (encrypted at rest)
  • TTL: 3600 seconds (auto-delete)
  • User isolation: Per session/character

Wallet Data:
  • Private keys encrypted via Coinbase SDK
  • Not directly exposed in backend
  • Sensitive data minimal in logs

Transaction Data:
  • Transaction hashes (public)
  • Stored for audit trail
  • Immutable on blockchain

Audit Logging:
  • All transactions logged
  • Agent decision logs
  • Timestamp & actor recorded
  • TTL policies for cleanup


7.5 Smart Contract Security Considerations
────────────────────────────────────────────────────────────────────────────────

Known Risks:
  • Uniswap slippage: Configurable tolerance
  • Gas estimation: May fail with insufficient gas
  • Reentrancy: Only calling trusted Uniswap contracts
  • Approval mechanism: ERC20 standard approval workflow

Mitigations:
  • Limit tool parameters (max gas, slippage)
  • Validate contract addresses before interaction
  • Use only audited, well-known contracts (Uniswap V2, Zora)
  • Error handling & transaction simulation


7.6 Compliance & Privacy
────────────────────────────────────────────────────────────────────────────────

Privacy:
  • Chat history auto-deletes (3600s TTL)
  • No personally identifiable information stored
  • User data isolated by session/authentication
  • No third-party data sharing

Compliance:
  • Blockchains are public (transactions visible on-chain)
  • Regulatory requirements vary by jurisdiction
  • No KYC/AML implemented (testnet focus)
  • Production deployment may require compliance layer

9. ERROR HANDLING & RESILIENCE
================================================================================

9.1 Error Handling Strategy
────────────────────────────────────────────────────────────────────────────────

Backend Error Handling:
  • Try-catch blocks around async operations
  • User-friendly error messages
  • Error logging to stdout (Cloud Logging)
  • WebSocket error handling

Network Errors:
  • Retry logic: Exponential backoff (external API calls)
  • Timeout handling: Graceful degradation
  • Fallback options: Alternative LLM providers

Blockchain Errors:
  • Insufficient gas: Suggest increased gas limit
  • Slippage exceeded: Adjust tolerance
  • Contract errors: Decode and explain

Tool Failures:
  • Individual tool failure doesn't crash agent
  • Agent continues with alternative tools
  • User notified of partial success


9.2 Fault Tolerance
────────────────────────────────────────────────────────────────────────────────

Connection Resilience:
  • WebSocket reconnection on client side
  • Server cleanup on connection drop
  • Pending messages queued/retried

Data Consistency:
  • Firestore transactions for critical operations
  • Chat history persisted after each message
  • Idempotent tool operations (no double-charge)

Graceful Degradation:
  • If external API unavailable: Return cached data or estimate
  • If LLM provider down: Fall back to alternative
  • If Firestore unavailable: In-memory cache (temporary)
